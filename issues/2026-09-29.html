JetBrains Air Teams: Share Agentic Workflows Across Your Whole Engineering Team

High Traction

JetBrains launched Air Teams on September 28 as part of the broader JetBrains Air platform for agentic software development. Air Teams lets you create reusable agentic workflow templates that the whole team can use, automating repeatable work like code reviews, test generation, and migration patterns. The platform integrates with JetBrains IDEs and supports custom agent instructions that encode team-specific coding standards and architectural decisions.

JetBrains Air Teams Agentic Workflows Team Productivity

Why it matters

Most AI coding tools are still individual productivity boosters — one developer, one agent session. JetBrains Air Teams tackles the harder problem: making agent-assisted workflows a team capability rather than a personal one. When one senior engineer figures out the right prompt and workflow for, say, migrating a service to a new API version, Air Teams lets them package that as a reusable template anyone on the team can run. This is the difference between 'we use AI' and 'AI is part of our engineering process.' For teams already deep in the JetBrains ecosystem (IntelliJ, WebStorm, PyCharm), this is the most friction-free path to team-wide agentic adoption.

Use cases

  • Packaging proven agent workflows as reusable team templates
  • Automating repeatable engineering tasks (reviews, migrations, test generation)
  • Enforcing team coding standards through agent instructions
  • Onboarding new team members with pre-built agentic workflows

Traction

  • Launched September 28 by JetBrains, one of the largest IDE companies
  • Covered by InfoWorld, JetBrains Blog, and developer community
  • Part of the broader JetBrains Air platform announced September 22
  • JetBrains has millions of active IDE users

Meta Releases Muse Glimmer 30B: An Open Model Built for Always-On Local Agents

High Traction

Meta released Muse Glimmer 30B, an Apache 2.0 open-weight model purpose-built for autonomous agentic tasks on consumer hardware. Distilled from the larger Muse Spark, the 30B-parameter model runs on a single GPU and is tuned specifically for tool use, long-running tasks, and failure recovery. It includes a dedicated perception encoder for multimodal capabilities. The model targets the 'always-on agent' use case — agents that persist, recover from errors, and manage state over extended sessions.

Meta Open Source Local AI Agent Model

Why it matters

The open-weight agent model space just got its strongest contender for local deployment. While most frontier models require cloud APIs, Muse Glimmer is explicitly designed to run on a single consumer GPU — making it practical for developers who want agent capabilities without API costs or data leaving their machine. The focus on failure recovery and long tasks addresses the real pain point with local agents: they crash, lose context, and can't handle multi-step workflows. Apache 2.0 licensing means you can embed it in commercial products without restrictions. For anyone building agent infrastructure that needs to work offline or in air-gapped environments, this is the model to evaluate.

Use cases

  • Self-hosted coding agents without cloud API dependencies
  • Local agent deployment in air-gapped or privacy-sensitive environments
  • Building always-on agents that survive crashes and recover state
  • Embedding agent capabilities in commercial products (Apache 2.0)

Traction

  • Released by Meta Superintelligence Lab, Apache 2.0 licensed
  • Available on Hugging Face and Meta's developer portal
  • 30B parameters runs on single consumer GPU
  • Distilled from Muse Spark with dedicated perception encoder
  • Covered by CtrlMag and developer community

OpenAI Ships Agents API: Build Cloud Agents with the Managed Codex Harness

High Traction

OpenAI launched the Agents API on September 10, giving developers programmatic access to the Codex harness — the same infrastructure that powers Codex and ChatGPT for Work. The API manages sessions, orchestration, context compaction, and recovery while your application provides the tools and environment. Agents run in sandboxed cloud environments and can execute code, browse the web, and use custom tools. Cloudflare immediately announced integration with Cloudflare Containers for running Codex agents.

OpenAI Agents API Codex Cloud Agents

Why it matters

This is OpenAI taking the infrastructure that makes Codex work and packaging it as a platform service. The key differentiator is the managed harness — session management, context compaction, and crash recovery are handled by OpenAI, so you focus on defining tools and business logic rather than building agent infrastructure from scratch. The Cloudflare Containers integration on day one signals that this is designed for production use, not just prototyping. For teams that have been building bespoke agent runtimes, this is the 'just use the managed service' option from the company that has the most experience running agents at scale.

Use cases

  • Building production agent applications without managing agent infrastructure
  • Running long-lived coding agents in sandboxed cloud environments
  • Integrating agent capabilities into existing applications via API
  • Deploying agents to Cloudflare edge infrastructure

Cursor Ships Rollouts and Security Review: Bots for the Last Mile of Shipping Code

Growing

Cursor launched two new bots on September 23 that extend AI assistance beyond code writing into deployment and security. Rollouts watches every change as it deploys and reports health per environment, built on technology from the Firetiger acquisition. Security Review scans every PR for exploitable bugs before merge. Together, they cover the gap between 'code written' and 'code safely in production' — the last mile that most AI coding tools ignore.

Cursor DevOps Security Deployment

Why it matters

Cursor is making a strategic bet that the value of AI in software development extends well past writing code. Rollouts is particularly interesting: it connects the code change to its production behavior, so when a deploy goes sideways, the bot can correlate it back to the specific diff that caused it. This is the kind of closed-loop feedback that makes AI coding assistants actually trustworthy — not just 'it wrote the code' but 'it verified the code works in production.' The Firetiger acquisition-to-product pipeline (acquired, then shipped a month later) shows Cursor executing fast on its vision of end-to-end agent coverage.

Use cases

  • Automated deployment health monitoring per environment
  • Pre-merge security scanning for exploitable vulnerabilities
  • Correlating production issues back to specific code changes
  • Closing the loop between code generation and production verification

Cloudflare Open-Sources Forge for SDK Generation After Anthropic Acquires and Shutters Stainless

High Traction

After Anthropic acquired Stainless and shut down its SDK generation service, Cloudflare open-sourced Forge — a pipeline for generating SDKs, CLIs, docs, and libraries from API specifications. This was part of a massive Cloudflare developer week that also included the launch of the agentic `cf` CLI (covering the entire Cloudflare API), EmDash 1.0 CMS with a secure plugin registry, and VoidZero/Vite+ integration. Google also released a competing open-source SDK generator in response to the Stainless shutdown.

Cloudflare Forge Open Source SDK Generation

Why it matters

Stainless was the de facto standard for generating typed SDK clients from OpenAPI specs — used by OpenAI, Anthropic, and Cloudflare themselves. When Anthropic acquired it and stopped offering the service to others, it left dozens of API companies scrambling. Cloudflare's response was to build and open-source an alternative within weeks, which is both impressive execution and a reminder of the risks of depending on proprietary tooling. For any team that generates client SDKs from API specs, Forge is now the open-source option that won't get acquired out from under you.

Use cases

  • Generating typed SDK clients from API specifications
  • Replacing Stainless in existing SDK generation pipelines
  • Maintaining multi-language client libraries from a single API spec
  • Building agentic CLI tools that cover entire API surfaces

Traction

  • Released September 28 by Cloudflare as open source
  • Direct response to Stainless shutdown affecting multiple companies
  • Covered by The New Stack and developer community
  • Cloudflare and Google both released alternatives simultaneously
  • Part of a major Cloudflare developer week

LangSmith Engine v2: Red Teaming and Fine-Tuning from Agent Trajectories

Growing

LangChain shipped two major LangSmith updates on September 24. Engine v2 adds automated red teaming that proactively discovers agent failure modes before they appear in production. Separately, LangSmith Fine-Tuning (via the `smithtune` CLI) lets you take agent trajectories stored in LangSmith and produce a fine-tuned model in one command — turning your production agent data into a smaller, cheaper, custom model.

LangChain LangSmith Red Teaming Fine-Tuning

Why it matters

Two underserved needs in one release. Red teaming agents is still mostly manual — someone has to think of adversarial inputs and edge cases. Engine v2 automates this, which matters because agents fail in surprising ways that are hard to predict upfront. The fine-tuning pipeline is equally important: most teams accumulate thousands of successful agent trajectories in LangSmith but have no easy way to distill that into a cheaper model. One CLI command to go from production traces to a fine-tuned model closes the loop on the 'start with a frontier model, then optimize costs' strategy that every serious agent deployment eventually needs.

Use cases

  • Automated adversarial testing of agent behaviors before production
  • Fine-tuning smaller models from production agent trajectories
  • Reducing inference costs by distilling frontier model behavior
  • Continuous agent quality improvement from production data

Docker Launches Cloud Sandboxes and Submits Sandbox Kit Spec to CNCF

High Traction

Docker shipped two complementary announcements on September 24. Cloud Sandboxes lets developers start agent workloads on their laptop and burst to elastic cloud environments when complexity scales up. Separately, Docker submitted the Sandbox Kit specification to the CNCF — an open standard for defining what an AI agent is allowed to do (file access, network, exec permissions) in a portable, declarative format. The spec is described as 'authority as code' — the OCI of agent permissions.

Docker CNCF Agent Security Sandbox

Why it matters

Docker is trying to do for agent permissions what they did for container images: create a portable standard. Right now, every agent platform defines permissions differently — Claude Code has CLAUDE.md, Cursor has its own rules, Codex has yet another format. Sandbox Kit proposes a single spec that travels with the agent regardless of where it runs. The CNCF submission is the power move: if this gets adopted as a CNCF standard, every Kubernetes-based platform will need to support it. Combined with Cloud Sandboxes (the runtime), Docker is positioning itself as the platform layer between agents and infrastructure. For platform engineers, this is the spec to watch — if it gains traction, it becomes the 'Dockerfile for agents.'

Use cases

  • Defining portable agent permissions that work across platforms
  • Bursting agent workloads from laptop to cloud seamlessly
  • Standardizing agent security policies across engineering organizations
  • Building compliant agent infrastructure on Kubernetes

Traction

  • Launched September 24 by Docker
  • Submitted to CNCF as an open specification
  • Described as 'authority as code'
  • Cloud Sandboxes provides companion runtime
  • Press release and multiple blog posts from Docker

Google Open-Sources AX: Kubernetes-Style Orchestrator for Autonomous AI Agents

Growing

Google open-sourced AX (Agent Executor) on September 22 under Apache 2.0. AX applies Kubernetes-style declarative manifests to agent workloads — you define Task, Workspace, Gateway, and Model resources in YAML, and AX handles sandbox provisioning, workspace wiring, and agent lifecycle. Built in Go, it hit #1 on Hacker News. Underneath AX sits Agent Substrate, Google's internal infrastructure play for agent execution at scale. The project has ~2K GitHub stars and 116 forks, but Google warns it's pre-stable with expected breaking changes.

Google AX Kubernetes Agent Orchestration

Why it matters

Google is applying the exact pattern that made Kubernetes successful to agent orchestration: declarative resource definitions, a control plane that reconciles desired vs. actual state, and pluggable backends. If you know kubectl, you already know the AX mental model. The separation of AX (the interface) from Agent Substrate (the infrastructure) mirrors the Kubernetes/cloud-provider split — platform-agnostic on top, cloud-optimized underneath. For teams already running Kubernetes, AX fits naturally into existing workflows. The #1 Hacker News ranking and 2K stars in the first week signal strong community interest, even with the pre-stability warning.

Use cases

  • Declarative agent workload orchestration on Kubernetes
  • Standardizing agent sandbox and workspace provisioning
  • Multi-agent fleet management with Kubernetes-native tooling
  • Building internal developer platforms for agent deployment

Traction

  • Open-sourced September 22 by Google under Apache 2.0
  • #1 on Hacker News
  • ~2K GitHub stars, 116 forks in first week
  • Covered by InfoQ and Forkast
  • Built in Go with Kubernetes-style architecture

AWS SageMaker HyperPod Inference Gateway: Eliminate GPU Waste in Multi-Model Serving

Growing

AWS launched SageMaker HyperPod Inference Gateway on September 24 — a service that routes inference requests across multiple LLM deployments to maximize GPU utilization. Instead of each model getting dedicated GPU allocation (and wasting capacity during low-traffic periods), the Inference Gateway pools GPU resources and routes dynamically based on load, latency requirements, and model priority. It supports mixed model deployments on the same GPU cluster.

AWS SageMaker GPU Inference

Why it matters

GPU costs are the biggest line item for teams running multiple LLMs in production, and most of those GPUs sit idle most of the time. HyperPod Inference Gateway tackles the same problem that Kubernetes solved for CPU workloads: bin-packing multiple workloads onto shared infrastructure to eliminate waste. For teams running different models for different use cases (a fast model for classification, a large model for generation, a code model for development), this means one GPU cluster instead of three. The dynamic routing based on load and latency is the key feature — it's not just load balancing, it's workload-aware scheduling for inference.

Use cases

  • Consolidating multiple LLM deployments onto shared GPU clusters
  • Dynamic routing of inference requests based on load and latency
  • Reducing GPU waste in production AI infrastructure
  • Mixed-model serving with workload-aware scheduling

Traction

  • Launched September 24 by AWS
  • Part of the SageMaker HyperPod platform
  • Addresses the #1 cost concern for multi-model deployments
  • Multiple AWS blog posts and documentation

Hugging Face Relore: Repository Memory That Makes Coding Agents Understand Your Codebase History

Emerging

Hugging Face published Relore on September 21 — a system that gives coding agents memory of a repository's history, patterns, and prior decisions. Instead of treating each coding session as a fresh start, Relore indexes past commits, PR discussions, issue resolutions, and code review feedback into a queryable memory that agents can consult. The project emerged from real Transformers repo maintenance where an agent used repository memory to correctly fix a GPTNeoXJapanese RoPE bug within a day.

Hugging Face Repository Memory Coding Agents Context

Why it matters

Coding agents are amnesiacs — every session starts from scratch, ignoring months of context about why code is structured a certain way. Relore addresses this by building persistent repository memory from the artifacts developers already produce (commits, PRs, reviews). The GPTNeoXJapanese fix is a compelling proof point: a contributor opened an issue about a RoPE bug, and an agent with repository memory found the fix by understanding how similar issues were resolved before. For large repositories with years of history, this kind of institutional memory could be the difference between an agent that proposes naive fixes and one that understands the codebase's actual conventions.

Use cases

  • Giving coding agents persistent memory of repository history
  • Enabling context-aware bug fixes that respect existing patterns
  • Building institutional knowledge into automated code maintenance
  • Improving agent performance on large, long-lived codebases

Traction

  • Published September 21 by Hugging Face
  • Demonstrated on the Transformers repository (one of the most active OSS ML repos)
  • Real-world proof: agent fixed GPTNeoXJapanese RoPE bug using repo memory
  • Built by Tarek Ziadé at Hugging Face
