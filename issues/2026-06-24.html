GitHub Spec-Kit: From Vibe Coding to Spec-Driven AI Development — 30+ Agent Integrations, One Workflow to Rule Them All

Growing

GitHub Spec-Kit (github/spec-kit) is an open-source toolkit that structures AI-assisted development into a four-stage workflow: specify → plan → tasks → implement. The specify stage produces a plan.md, data-model.md, research.md, and quickstart.md from a natural-language description. The implement stage runs any connected coding agent against the task list. As of June 2026, Spec-Kit integrates with 30+ AI coding agents — including Claude Code, GitHub Copilot, Cursor, Gemini CLI, Windsurf, Amp, Codex CLI, Roo Code, Kilo Code, and OpenCode — and is model-agnostic at each stage. The project is developed by GitHub and documented at speckit.org. The key problem it solves: AI coding agents given an open-ended prompt drift, hallucinate requirements, and produce inconsistent implementations. Spec-Kit enforces a structured decision record before any code is written.

GitHub Spec-Kit Spec-Driven Development AI Coding Multi-Agent Developer Workflow Open Source Code Quality

Why it matters

Spec-Kit addresses the failure mode that is increasingly cited as the real bottleneck in AI-assisted development: not code generation speed, but the verification overhead of reviewing what agents produce when they work from vague prompts. The four-stage workflow shifts the AI's work upstream — instead of asking the agent to 'build a user authentication system,' Spec-Kit first asks the agent to produce a spec document that you review and approve before any code is written. This dramatically reduces the scope of verification: you review a two-page spec once, approve it, and then the agent implements against that contract. The 30+ agent integration matrix makes Spec-Kit model-agnostic: you can run specify with Claude Code, plan with Cursor, and implement with OpenCode — or use a single tool for all stages. This portability matters as the coding agent landscape continues to shift (Gemini CLI → Antigravity, OpenAI Codex deprecation cycles). The specify → plan → tasks → implement pattern is also the structure that enterprise software processes already use: writing a spec before coding is not a new idea, but Spec-Kit is the first tool to wire this into AI coding agent workflows as a first-class primitive. For teams struggling with agent drift in larger codebases, this is the structural fix that prompt engineering alone can't provide.

Use cases

  • Replace open-ended agent prompts with a Spec-Kit specify stage for every feature above 50 lines: run the specify CLI against your feature description, review the generated plan.md and data-model.md, edit for accuracy, then hand off the approved spec to your coding agent — this shifts the agent's first failure mode (misunderstanding requirements) to a reviewable document rather than a discovered bug
  • Use Spec-Kit's tasks stage to build verifiable checklists for multi-agent workflows: the tasks output is a structured checklist that each agent step can mark done as it completes — this gives you an audit trail of what was implemented and what remains, which is essential when a Claude Code session runs for 45 minutes and you need to understand its progress
  • Wire Spec-Kit into your GitHub PR template: run specify on each PR description to generate a data-model.md and quickstart.md as PR artifacts — reviewers can check the spec document against the diff, making PR review faster because the intent is explicit rather than inferred from code
  • Evaluate Spec-Kit for onboarding junior engineers to AI-assisted development: the specify → plan → tasks → implement workflow teaches the mental model of writing requirements before code, which is both a software engineering best practice and the skill that makes AI agent outputs more reliable — Spec-Kit makes this pattern enforced rather than aspirational

Agentjacking: One Fake Sentry Error Hijacks Claude Code, Cursor, and Codex — 2,388 Organizations Exposed

High Traction

Tenet Security published research in June 2026 documenting 'agentjacking' — a novel attack class that exploits the intersection of Sentry's open event-ingestion architecture and the implicit trust model of MCP-connected AI coding agents. The attack requires only a Sentry DSN (Data Source Name) — a public, write-only credential discoverable in any browser's JavaScript source or via a one-line GitHub search. An attacker posts a malicious Sentry error event containing Markdown-injected shell commands. When a developer asks their AI coding agent to 'fix unresolved Sentry issues,' the agent fetches the event via the Sentry MCP server and executes the attacker-controlled commands with the developer's full system privileges. Tenet confirmed an 85% exploitation success rate against Claude Code, Cursor, and Codex in testing, and identified 2,388 organizations with injectable DSNs as of June 12, 2026 — 71 of which rank in the global Tranco top-1 million websites. Sentry added a content filter after disclosure on June 3 but characterized a root-cause fix as not feasible.

Agentjacking Security MCP Sentry Claude Code Cursor Codex Prompt Injection Supply Chain Coding Agents Tenet Security

Why it matters

Agentjacking is the first disclosed attack class that exploits AI coding agent workflows specifically, and it is highly accessible: the attack requires no zero-day, no special access, and no exploit code beyond a crafted HTTP request to a public endpoint. The 'Authorized Intent Chain' is the reason traditional defenses fail — every action in the attack is technically authorized. The developer authorized the agent to access Sentry. The agent authorized the shell execution as part of its normal workflow. The Sentry MCP server returned real-looking error data. There is no anomaly for an EDR, WAF, or SIEM to catch. The 85% success rate across three major coding agents (Claude Code, Cursor, Codex) means this is not a narrow edge case — it reflects the default trust model that all three tools apply to MCP-connected data sources. The credentials that an agentjacking attack can extract are extremely high-value: AWS access keys, GitHub OAuth tokens, Kubernetes service account tokens, Sentry authentication tokens, and npm package registry credentials all live in a typical developer's environment. A successful attack does not just compromise the developer's machine — it can expose CI/CD pipelines, production cloud infrastructure, and private repositories. The immediate action for any team using Sentry MCP is to audit what permissions your coding agent has in your environment and whether Sentry MCP access should be gated behind an explicit confirmation prompt rather than automatic execution.

Use cases

  • Audit your Sentry MCP configuration for implicit-execution exposure: in Claude Code, Cursor, or Codex, check whether your Sentry MCP server is configured to allow the agent to fetch and act on error data without an explicit confirmation step — if your agent can read Sentry errors and execute code without a HITL checkpoint, you are exposed; add a confirmation prompt before any action triggered by fetched Sentry data
  • Search your public GitHub repositories for accidentally exposed Sentry DSNs: run a GitHub code search for your organization's Sentry organization slug combined with 'publicKey' or 'dsn' — if a DSN is in a public JavaScript bundle or a committed config file, rotate it immediately; Sentry DSNs are intentionally public by design, but rotating one that has been exposed removes the attack surface
  • Add a MCP server allowlist and block Sentry MCP from running unconfirmed shell commands: configure your coding agent to treat data from Sentry MCP as untrusted input — require explicit developer confirmation before any tool call that originates from a Sentry-fetched event; this is the same principle as requiring confirmation before 'git reset --hard' but applied to data-triggered actions
  • Brief your security team on the Authorized Intent Chain attack model: agentjacking bypasses all perimeter controls because every action is technically authorized — your security team's threat model almost certainly does not include 'attacker manipulates content in a monitoring tool that the AI agent then acts on'; update your threat model and run a tabletop exercise using the Tenet Security PoC as the scenario

Model Routing in 2026: How Production Teams Are Cutting LLM Spend 60-86% Without Sacrificing Quality

Growing

With Fable 5 paywall starting June 23 and GitHub Copilot billing shock driving 10x-50x cost increases on agentic workflows, model routing has become the highest-leverage cost engineering technique in production AI. The core strategy: send easy tasks to cheap models ($0.30-3/M tokens) and complex tasks to frontier models ($10-50/M). Teams that have implemented tuned routing layers report 60-86% total cost reductions without detectable quality regressions. A specific benchmark: routing 70% of traffic to Flash-class models ($0.30/M), 20% to mid-tier ($3/M), and reserving 10% for frontier ($15/M) drops average cost from $15 to $2.10 per million tokens — an 86% reduction. Combined with prompt caching (40-90% savings on input tokens) and context window management (30-60% savings), production teams are achieving 60-80% total cost reduction. Tools implementing routing today: LiteLLM (open-source proxy), Requesty.ai (routing API), Portkey (gateway with routing), and Databricks Unity AI Gateway (enterprise).

Model routing has moved from a cost optimization technique to a production necessity following June 2026's billing events. The Fable 5 paywall at $50/M output tokens and GitHub Copilot's move to token-based AI Credits have broken the 'unlimited frontier model' assumption that most agent architectures were built on. Teams that built their agent stacks assuming flat subscription pricing are now discovering that their per-task costs were never visible to them before. The practical implication: if your agent currently sends every task to the same model, you are almost certainly overpaying by 3-10x. Most production workloads contain a natural mix of easy tasks (classification, summarization, structured extraction) and hard tasks (code generation, multi-step reasoning, complex debugging). The easy tasks should not be going to GPT-5.5 or Opus 4.8. Routing logic does not have to be complex to be effective: even a simple rule ('if the input is under 500 tokens and the task type is extraction, use Haiku 4.5') can cut your bill by 30-40% with no quality regression on those task types. The more sophisticated implementations use a lightweight routing model that classifies task complexity and selects the appropriate tier in under 10ms — adding negligible latency while reducing cost by 60-80%.

Use cases

  • Implement a 3-tier routing rule in your LLM client today without tooling: classify tasks by type — (1) fast/cheap: classification, extraction, summarization, Q&A → route to Haiku 4.5 or Flash; (2) standard: code completion, review, moderate analysis → route to Sonnet 4.6 or equivalent; (3) frontier: architectural refactors, complex debugging, multi-file agentic work → route to Opus 4.8 or GPT-5.5; this single change cuts average cost 40-60% with no new tooling
  • Add prompt caching for repeated context in agentic workflows: if your agents prefix every call with the same system prompt, code context, or documentation excerpt, enable Anthropic or OpenAI prompt caching (40-90% savings on cached input tokens) — for agents that make 20+ sequential calls with a shared context, caching turns every call after the first into a dramatically cheaper cached hit
  • Use LiteLLM (30K+ stars, MIT) as a routing proxy in front of your existing LLM calls: LiteLLM provides a drop-in OpenAI-compatible endpoint that routes to any provider; configure routing rules in a YAML file, add fallback providers for resilience, and enable cost tracking by model — you get routing, cost attribution, and provider fallback in a single self-hosted proxy without changing your application code
  • Audit your top 10 highest-cost agent workflows and bucket them by task complexity: pull your last 30 days of API usage from Anthropic or OpenAI console, identify the 5 workflows consuming the most tokens, and assess for each whether frontier-model quality is actually required; for each workflow where mid-tier quality is acceptable, route to the cheaper model and measure quality regression on a 100-task sample before committing to production
