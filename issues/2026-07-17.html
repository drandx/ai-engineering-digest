JetBrains Junie Exits Beta: #1 on SWE-Rebench at 61.6%, Runs the Real IDE Debugger, Zero External Tool Connections Required

Growing

JetBrains' AI coding agent Junie left beta in June 2026, with a July 2026 state-of-play assessment placing it as the top model-harness on SWE-Rebench (the independent successor to SWE-bench for agent-harness evaluation) at 61.6% resolved and 72.7% pass@5. Junie is architecturally distinct from terminal-based agents like Claude Code, Grok Build, and OpenCode: it runs entirely inside JetBrains IDEs (IntelliJ IDEA, PyCharm, WebStorm, GoLand, Rider) with direct access to the IDE's file tree, build system, run configurations, test runner, version control, and — critically — the real debugger. Junie plans before coding (generates a structured edit plan before making file changes), debugs using the IDE's actual debug step-through rather than print statements or error text, reviews PRs with full project context, and handles long background tasks while the developer focuses on other work. No external MCP server setup, no tool connection configuration — Junie's tooling is the IDE itself.

JetBrains Junie IntelliJ PyCharm AIAgent SWERebench IDEAgent Debugger CodeReview OutOfBeta

Why it matters

Junie's architectural bet — run the agent inside the IDE rather than in a terminal alongside it — resolves a real pain point that terminal-based agents have. When Claude Code or Grok Build hits a runtime error, it reads the error message in text and tries to infer what went wrong. When Junie hits a runtime error, it can set a breakpoint and step through the call stack in the actual IntelliJ debugger, reading variable state directly rather than inferring from log output. This distinction matters most for debugging tasks: a terminal agent that can only observe error text has to write diagnostic code to expose the state it can't see; a debugger-connected agent can inspect it directly. The 61.6% SWE-Rebench result is notable because SWE-Rebench is a harness-evaluation — it scores the full model-plus-agent combination, not just the model alone. Junie's performance is therefore a compound signal: strong enough model capability (JetBrains hasn't published which underlying model powers Junie), strong enough IDE integration, and strong enough planning behavior to rank #1 on an agent-harness evaluation. For the large population of engineers who already use IntelliJ-family IDEs as their primary environment — especially Java, Kotlin, Python, and Go developers who have deeply customized IntelliJ project setups — Junie is the path of least resistance to production-quality AI-assisted coding: no new CLI tools, no second terminal session, no MCP configuration. The plugin installs from JetBrains Marketplace and the agent is aware of your existing project configuration immediately.

Use cases

  • Install Junie from JetBrains Marketplace and use it for your hardest debugging sessions instead of your terminal coding agent: when you have a failing test or runtime error that requires understanding internal state (not just reading the error message), use Junie to step through the call stack in IntelliJ's real debugger; Junie can set breakpoints, observe variable values at each frame, and iterate on code changes within the same debugger session — this is the task type where a native IDE agent provides the most concrete advantage over terminal agents that can only read error text
  • Use Junie's planning mode for multi-file refactors before execution: Junie generates a structured edit plan that lists each file it intends to change and what change it will make before executing; review the plan for correctness (checking that the right files are in scope, that the change description matches your intent) before approving execution; this review step catches scope errors (editing files you didn't intend to modify) before any code changes are made, which is the most common cause of agent-assisted refactor failures
  • For PR reviews with JetBrains, let Junie run the review with full project context: Junie has access to your project's build system, type system, and test runner during PR review — it can validate that a change compiles, run the affected test suite, and evaluate the change against the project's existing patterns in a way that a language model reviewing the raw diff cannot; use Junie's PR review output as a first pass that catches build-breaking changes and test regressions, then apply your own judgment to the design and logic questions

OpenTelemetry GenAI Semantic Conventions: The Emerging Standard for LLM, Agent, and MCP Observability — Datadog Native Support, LangChain/CrewAI/AutoGen Emit OTel Spans

Growing

OpenTelemetry graduated from the CNCF in May 2026 with its GenAI Semantic Conventions reaching production maturity — a standardized attribute schema for capturing LLM calls, agent orchestration traces, MCP tool invocations, and AI quality metrics within the OTel span model. The conventions specify: gen_ai.request.model (the model being called), gen_ai.usage.input_tokens and gen_ai.usage.output_tokens, gen_ai.response.finish_reasons, gen_ai.tool.name and gen_ai.tool.call.id for tool invocations, and opt-in content capture (full prompt and completion text) via events rather than span attributes. Datadog published native OTel GenAI Semantic Convention support in a July 2026 blog post. LangChain, CrewAI, AutoGen, and AG2 now emit OTel-compliant spans natively or via instrumentation packages. MLflow documents OTel GenAI conventions in its official tracing documentation. Greptime published a technical deep-dive on how the conventions trace LLM calls, agent reasoning, and MCP tool calls in a unified span model.

OpenTelemetry GenAI SemanticConventions LLMObservability CNCF Datadog LangChain MCP AgentTracing Production

Why it matters

The fragmentation problem in LLM observability has been real: every observability vendor (Langfuse, Arize, LangSmith, Datadog, Honeycomb) has used proprietary span formats for LLM traces, meaning that switching vendors or adding a second tool requires re-instrumenting your application. OpenTelemetry GenAI Semantic Conventions end this: once your application emits OTel-compliant GenAI spans, any OTel-compatible backend (Datadog, Honeycomb, Grafana, Jaeger, your own collector) can receive and query those traces without application changes. The framework-level emission is the adoption accelerant: if you use LangChain, CrewAI, AutoGen, or AG2, you are likely already emitting OTel-compliant spans in your current version without any configuration — the frameworks added instrumentation packages that do it automatically. The MCP tool tracing coverage is the AI engineering-specific advance: OTel GenAI conventions now standardize how MCP tool call initiation, tool response, and tool error are captured within agent traces; you can see exactly which MCP tool was called, with what arguments, what it returned, and how long it took, in the same trace view as the LLM calls that triggered it. For teams building multi-agent systems where a request flows across multiple model calls and MCP tool invocations, a single unified trace that covers the entire path — from user request through agent reasoning through tool calls through final response — is the operational visibility primitive that makes debugging production agents tractable.

Use cases

The Most-Watched AI Infra Benchmark of Q3: Terminal-Bench 2.1 Is Now the Industry Standard for End-to-End Agent Evaluation

Growing

As of July 2026, Terminal-Bench 2.1 has emerged as the primary benchmark for evaluating AI coding agents — both models and agent-harness combinations — on end-to-end task completion in a real terminal environment. The benchmark runs agents against real software engineering tasks in a live Linux terminal with actual codebases, real test runners, and real build systems, measuring whether the agent achieves the intended outcome (all tests pass, the build succeeds, the feature works) rather than whether generated code looks correct in isolation. The July 2026 top scores: Grok 4.5 at 83.3%, Claude Fable 5 at ~80%, OpenCode with GLM-5.2 at 81.0%, JetBrains Junie at 61.6% (SWE-Rebench). The Thoughtworks Technology Radar, the State of Open Source AI report, and multiple practitioner surveys now reference Terminal-Bench 2.1 as the benchmark to check first when evaluating coding agents for production use.

Why it matters

The proliferation of AI coding benchmarks (HumanEval, MBPP, SWE-bench original, SWE-bench Pro, Terminal-Bench 1.x, DeepSWE, SWE-Rebench, CursorBench) has created a credibility problem: vendors publish the benchmark where their model scores best, and engineers are left without a single shared reference point for 'which agent actually completes real coding tasks.' Terminal-Bench 2.1 has resolved this through a combination of design properties that competitors haven't matched: it tests in a real Linux environment (not sandboxed Python execution), it requires end-to-end task completion (not just generating a diff), it uses a fresh codebase per task (preventing memorization), and it measures pass@1 (first attempt success) which is the metric that matters for production agentic workloads where retrying a 5-minute task is costly. The convergence of the AI engineering community on Terminal-Bench 2.1 as the primary evaluation reference — cited independently by Thoughtworks, the State of Open Source AI report, LogRocket, and multiple practitioner guides in the same month — is the benchmark credibility signal. For teams building their own internal coding agent evaluations, the Terminal-Bench design principles (live environment, end-to-end task completion, pass@1 measurement, fresh codebases) are the quality standards to match when building your own benchmark for your specific workload.

Use cases

  • Use Terminal-Bench 2.1 scores as your first filter when evaluating coding agents: sort by Terminal-Bench 2.1 score to get the initial ranking (Grok 4.5 83.3%, Fable 5 ~80%, GLM-5.2 81.0%, Junie 61.6% harness-only), then narrow to your cost bracket (GLM-5.2 at $1.40/M for cost-sensitive, Fable 5 at $10/M for quality-first), then run your own evaluation on tasks from your specific codebase and language stack; Terminal-Bench 2.1 tells you baseline end-to-end completion capability, but your workload distribution may favor a different ranking
  • Build your internal coding agent benchmark with Terminal-Bench design principles: use a live terminal environment (Docker container with your standard dev environment), require end-to-end task completion (tests pass, build succeeds), measure pass@1 (first attempt only, no retries), and use fresh task variants for each evaluation run (no cached task state between evaluations); these four properties eliminate the confounders (sandboxed execution, code-only evaluation, retry allowances, test set memorization) that make most synthetic benchmarks poor predictors of real production performance
  • When a vendor's coding agent benchmark exceeds Terminal-Bench 2.1 scores significantly on a proprietary benchmark, check for training data overlap: the Grok 4.5/CursorBench contamination case establishes the failure mode — a model can score anomalously high on a benchmark whose evaluation tasks share characteristics with its training data; when a model scores 15%+ above its Terminal-Bench 2.1 performance on a proprietary benchmark, the first hypothesis to investigate is training-eval overlap, not genuine capability advantage
